# PRD — Дашборд капитала (личный + компания)

Документ описывает, каким должен стать дашборд после доработки. Каждая фича
описана с продуктовой точки зрения: что видит пользователь, как считается,
откуда берутся данные.

Вся денежная индикация — в долларах США ($). Рублёвые суммы (расходы) пересчитываются
в доллары по курсу ЦБ РФ на дату.

---

## 1. Личный капитал: единая модель

«Личный капитал» — это большая цифра вверху личного дашборда. Она равна сумме
четырёх частей:

- **Крипта** — текущая рыночная стоимость крипто-холдингов, подтягивается автоматически.
- **Авто** — стоимость автомобилей, вносится вручную.
- **Прочее** — прочие личные активы, вносятся вручную.
- **Свободные деньги** — доступный кэш (см. фичу 3).

Капитал компании в эту цифру не входит — компания считается отдельно, на своей вкладке.
Понятия «доступно к выводу» в личном контуре нет (оно живёт только у компании).

---

## 2. Автоматический сбор данных

Дашборд тянет данные из разных источников и держит их актуальными без участия пользователя
там, где это возможно.

- **Крипта (личная и компании)** — балансы кошельков подтягиваются из блокчейна по
  отслеживаемым адресам (Bitcoin, Ethereum, BNB Smart Chain, Tron, TON; кошельки компании —
  USDT в сетях Tron (TRC20), BSC (BEP20) и Ethereum (ERC20)).
  Стоимость в долларах считается по рыночным котировкам. Обновление — автоматически по
  расписанию (крипта — несколько раз в день) и по кнопке «обновить».
- **Расходы** — из Google Sheets (лист «Отчёт»), с пересчётом ₽→$ по курсу ЦБ. Обновление —
  по расписанию (примерно раз в час) и по кнопке.
- **Рекламные агентства (компания)** — остатки подтягиваются автоматически из ежедневного
  отчёта в рабочем Telegram-чате: сотрудник публикует одно сообщение со списком агентств и
  сумм, дашборд читает его ботом и обновляет балансы (подпись «кто внёс» = автор сообщения,
  отметка даты обновления). Ручная правка суммы сохраняется как резервный путь — следующий
  отчёт её перезапишет. Обновление — по расписанию (примерно раз в 15 минут) и по кнопке.
- **Авто / прочее / стартовый остаток свободных денег (личное)** — вносятся вручную и
  редактируются пользователем в любой момент.
- **Резервы компании (зарплаты, тех. расходы)** — задаются пользователем ползунками.

Каждый блок данных показывает, когда он последний раз обновлялся.

---

## 3. Свободные деньги: дивиденды и расходы

«Свободные деньги» — это часть личного капитала, отражающая доступный кэш. Считается так:

**Свободные деньги = стартовый остаток + сумма всех дивидендов − сумма всех расходов.**

- **Стартовый остаток** — сумма, которую пользователь задаёт вручную один раз (свой текущий
  кэш на момент старта). Редактируется при необходимости.
- **Дивиденды** — поступления денег из компании в личное (см. фичу 4). Каждое такое поступление
  увеличивает свободные деньги.
- **Расходы** — траты из Google Sheets. Каждый расход уменьшает свободные деньги.

Такая схема исключает двойной счёт: крипта и авто оцениваются отдельно (живьём / вручную),
а дивиденды и расходы влияют только на кэш.

В личном контуре пользователь видит свободные деньги отдельной величиной и понимает, из чего
она сложилась: стартовый остаток, приток дивидендов, отток на расходы.

---

## 4. Дивиденды: автоматически из компании

Когда деньги выводятся из компании в личное, это автоматически засчитывается как дивиденд —
поступление в личный капитал (в «свободные деньги»).

- Вывод средств из компании фиксируется как операция вывода в контуре компании.
- Каждая такая операция автоматически становится дивидендом на ту же сумму в личном контуре —
  пользователю не нужно вносить её повторно вручную.
- Дивиденд имеет дату и сумму; список поступивших дивидендов виден в личном контуре.

Так движение денег между контурами отражается согласованно: у компании сумма к выводу
уменьшается, у пользователя свободные деньги растут.

---

## 5. Состав капитала: из чего он состоит

На личном дашборде есть блок «Состав капитала», который показывает структуру капитала
по классам активов:

- **Крипта**, **Наличные (свободные деньги)**, **Авто**, **Прочее** — каждая категория с долей
  в процентах и суммой в долларах.
- Внутри **крипты** доступна разбивка по конкретным монетам (например, BTC, ETH, USDT, TON),
  а монеты — по адресам-кошелькам, на которых они лежат.

Пользователь сразу видит, какой класс активов сколько весит и из каких монет/кошельков
складывается крипто-часть.

---

## 6. История капитала во времени

Дашборд показывает, как капитал меняется во времени, на основе реальных данных (не демонстрационных).

- **Ежедневный снимок.** Раз в день автоматически сохраняется текущее значение. Сохраняются три
  показателя: общий личный капитал, стоимость крипто-портфеля (раздел «Инвестиции») и общий баланс
  компании. История накапливается со дня запуска и далее.
- **Графики на реальных данных.** Графики «общий личный капитал», «крипто-портфель» и «баланс
  компании» строятся из сохранённых снимков.
- **Переключатель периода (1М / 6М / 1Г).** Пока истории накоплено мало, график показывает столько
  данных, сколько реально есть, без искусственного растягивания. Если выбран период длиннее, чем есть
  данных, отображается доступный отрезок.
- **Изменение «+X% за месяц».** Рядом с суммой капитала показывается изменение за последний месяц:
  текущее значение сравнивается со значением примерно месяц назад. Если истории меньше месяца — со
  самым ранним доступным значением.

История компании переводится на ту же логику, что и личная: ежедневные снимки (вместо прежних
понедельных), чтобы оба контура были единообразны и сравнимы.

---

## 7. Поведение при устаревших или недоступных данных

Если источник данных недоступен или давно не обновлялся (нет связи с блокчейном, не пришли
котировки, агентство давно не обновляли), дашборд:

- **Показывает последнее известное значение** — цифры не прячутся и не обнуляются.
- **Ставит пометку «обновлено N назад»** рядом с соответствующим блоком.
- **Мягко подсвечивает устаревшие данные** (например, давно не обновлявшийся баланс агентства),
  чтобы было видно, что значение пора освежить.

Навязчивых блокирующих предупреждений нет — пользователь всегда видит актуальную картину с
честной отметкой свежести.

## 8. Компания: доступно к выводу

Контур компании сохраняет существующую логику расчёта.

- **Общий баланс компании = кошельки USDT + рекламные агентства.**
- **Доступно к выводу = общий баланс − резерв на зарплаты − резерв на тех. расходы −
  резерв на рекламные агентства − кредиторская задолженность CoinLink**, где резерв
  на зарплаты = недельный ФОТ × число недель в запасе.
- **Резерв на рекламные агентства** — ручной буфер, регулируется ползунком (what-if).
  Обычно ставится так, чтобы остатки агентств + резерв = $40k; под ползунком
  показывается текущая сумма «остатки + резерв». Вычитается из «доступно к выводу».
- **Кредиторская задолженность CoinLink** — текущая открытая кредиторка (`is_outstanding`)
  из внешней read-only БД CoinLink (представление `coinlink_payable`), за период
  **с 1 февраля текущего года по дату просмотра**. Цифра совпадает с дашбордом BI
  «ЦУ Payments» → «Кредиторская задолженность», подтягивается автоматически и
  доступна с разбивкой по партнёрам. Вычитается из «доступно к выводу».
- Резервы регулируются ползунками (what-if): «доступно к выводу» пересчитывается мгновенно.
- Кошельки компании сгруппированы (чистые / грязные — основные / грязные — мелкие), агентства
  редактируются вручную.
- Операция вывода средств (фича 4) фиксируется как событие и автоматически создаёт дивиденд в
  личном контуре. Саму сумму баланса/«доступно к выводу» она напрямую не уменьшает — фактический
  отток USDT отражается автоматически при следующем синке кошельков (см. фичу 9).

## 9. Уточнения по расчётам (решения по открытым вопросам)

Этот раздел уточняет и при расхождении имеет приоритет над формулировками фич 3, 4, 6 и 8.
Он закрывает места, где исходный текст допускал двойное толкование и грозил двойным счётом денег.

### 9.1. Свободные деньги считаются от даты старта

Чтобы исключить двойной счёт, у стартового остатка есть привязанная **дата «как на»** —
момент, на который зафиксирован текущий кэш.

- **Свободные деньги = стартовый остаток + дивиденды и − расходы, случившиеся ПОСЛЕ даты старта.**
- Расходы и дивиденды с датой раньше стартовой в расчёт не входят: они уже «прожиты» и учтены
  в самом стартовом остатке.
- Пользователь задаёт и сумму стартового остатка, и его дату; обе величины редактируются.
- Если свободные деньги уходят в минус (расходы превысили остаток и приток дивидендов),
  величина показывается как есть (отрицательной), без обнуления; в составе капитала (фича 5)
  такая отрицательная «наличная» доля не растягивает диаграмму в ноль — отображается честно.

### 9.2. Операция вывода: только лог и дивиденд

Вывод средств из компании — это **запись о событии**, а не корректировка баланса.

- Операция вывода имеет дату и сумму и автоматически создаёт дивиденд на ту же сумму в личном
  контуре (фича 4).
- Баланс компании и «доступно к выводу» эта операция напрямую **не уменьшает**: реальный отток
  USDT с кошелька отразится сам при следующем автоматическом синке (фича 2). Так исключается
  двойной счёт (отдельно «минус по операции» и отдельно «минус по синку»).
- Список операций вывода виден в контуре компании — как журнал движения денег между контурами.

### 9.3. Дивиденды: авто из вывода плюс ручной ввод

Основной источник дивидендов — операции вывода (фича 4), но ручной ввод сохраняется.

- **Автоматические дивиденды** создаются из операций вывода и связаны с ними.
- **Ручные дивиденды** можно добавить отдельно — для денег, пришедших в личное не через
  отслеживаемые кошельки компании (например, наличными или иным путём).
- В личном контуре список дивидендов показывает оба типа единым потоком поступлений; для каждого
  видны дата и сумма.

### 9.4. Переход истории компании на ежедневные снимки

При переводе компании с понедельных снимков на ежедневные (фича 6) накопленные данные сохраняются.

- **Старые понедельные точки остаются** в истории как есть.
- **Новые снимки копятся ежедневно**, наравне с личным контуром.
- График строится по всем доступным точкам; слева (старый период) плотность точек ниже, дальше —
  ежедневная. Искусственного пересчёта старых точек не делается.

### 9.5. Баланс TRX: учитывается только свободный

Для кошельков в сети Tron в капитал засчитывается только **свободный (ликвидный) TRX** —
средства, доступные к трате прямо сейчас. Замороженный/застейканный TRX (заморозка ради
ресурсов сети и права голоса, в т.ч. делегированный) в баланс **не включается**.

- Так значение в дашборде отражает доступные деньги, а не суммарное с учётом заморозок.
- Для USDT в сети Tron (TRC20) баланс читается напрямую у контракта токена — это надёжный
  источник; кэш-список токенов на аккаунте использоваться не должен, он бывает неполным.
- При недоступности сети баланс TRON-кошелька не обнуляется, а сохраняется последним
  известным значением с пометкой свежести (см. §7).

## 10. Журнал реализации (выполненные действия)

Раздел фиксирует уже выполненные по этому ТЗ доработки, чтобы история решений и
изменений была видна прямо в документе.

### 2026-06-10 — Личное: ввод актива в рублях с автопересчётом в $

- **Запрос.** При добавлении актива (например, автомобиль) уметь вводить сумму
  в рублях; в списке активов и на дашборде показывать её в долларах по
  актуальному курсу.
- **Реализация.** В модалке «Добавить актив» у ручных категорий (наличные /
  авто / ценная вещь / прочее) появился выбор валюты **₽ / $** с живым превью
  «≈ $…». Рублёвый актив хранит исходную сумму в `Asset.nativeValue` и
  `currency="RUB"` (миграция `20260610170000_asset_currency`), а `value` всегда
  в долларах. Пересчёт ₽→$ идёт по курсу ЦБ (тот же `getUsdRubRates`, что и
  расходы): один раз при сохранении и **заново при каждой загрузке**
  (`getPersonalData`), поэтому долларовая оценка всегда актуальна. В списке и в
  карточке дашборда под суммой показывается исходные «₽… · по курсу ЦБ».
- **Курс** отдаётся на клиент (`usdRub` в `PersonalData`) для превью в модалке.

### 2026-06-10 — Личное: актив «TON номера» с автоподтягом курса (nums888.io)

- **Запрос.** В личных активах нужны TON номера (анонимные +888): пользователь
  вводит их **количество**, а **стоимость** подтягивается автоматически по
  актуальному курсу 1 анонимного TON номера с https://nums888.io/. Курс показать
  рядом с активом.
- **Реализация.** Новая категория **«TON номера»** в модалке «Добавить актив»:
  вместо суммы вводится количество (шт). Актив хранится как обычный `Asset`
  (`symbol = "TONNUM"`, `amount` = количество, `bucket = other` → попадает в
  «Прочее» в составе капитала), а **значение `value = количество × курс`**
  пересчитывается автоматически. Количество редактируется прямо в списке активов
  (карандаш-ползунок), удаление — как у ручных активов.
- **Источник курса.** Курс 1 анонимного TON номера берётся с **nums888.io** —
  ровно как просил заказчик. Страница серверно-рендерная и содержит актуальный
  курс прямо в `<title>` (`$2788.50 | Telegram Anonymous Numbers`), поэтому
  долларовое число читается напрямую из HTML — без API, SPA и конвертаций.
  Провайдер `src/lib/tonnums/price.ts` парсит `$NNNN` из заголовка (фолбэк — по
  телу). Диагностика: GET `/api/sync/tonnums` (под сессией) показывает, что
  распозналось; GET `/api/sync/tonnums?probe=1` — какие хосты доступны с сервера.
  *(История: сначала пробовали getgems-флор, но api.getgems.io режется исходящим
  фильтром VPS — 403; зато nums888.io с VPS доступен и отдаёт цену в `<title>`.)* Синк
  `src/lib/sync/tonnums.ts` → эндпоинт `/api/sync/tonnums` кэширует цену
  (`PriceCache["TONNUM"]`), переоценивает все TON-номерные активы и пишет
  `SyncState["tonnums"]`. Воркер дёргает синк по расписанию
  (`SYNC_TONNUMS_CRON`, по умолчанию ежечасно) и один раз на старте; при
  добавлении актива синк запускается сразу.
- **Где виден курс.** Рядом с активом (и в списке «Активы», и в подсказке
  модалки) показывается «курс $X / номер · флор · обновлено N назад» со ссылкой
  на коллекцию на getgems.
- **Устойчивость (§7).** При недоступности источника синк падает ДО записи —
  последняя известная цена и значения активов сохраняются, бейдж свежести
  остаётся на времени последнего успеха. Без обнуления.
- **Конфигурация.** Источник настраивается без коммита кода:
  `TONNUM_COINGECKO_NFT_ID` (id коллекции на CoinGecko), `COINGECKO_API_URL`,
  `COINGECKO_API_KEY` (опц., поднимает лимиты), либо жёсткая фиксация цены
  `TONNUM_PRICE_USD`.

### 2026-06-09 — Компания: резерв на рекламные агентства

- **Запрос.** В расчёт «доступно к выводу» добавить ещё один ползунок и показатель
  **«Резерв на рекламные агентства»**, чтобы вручную выбирать сумму резерва.
  Обычно ставится так, чтобы остатки агентств + резерв = $40k.
- **Реализация.** Новое поле `agencyReserve` в модели `Reserve` (миграция
  `20260609160000_agency_reserve`, default 0). Ползунок добавлен в блок
  «Резервы — what-if» во всех трёх раскладках (дашборд / калькулятор / отчёт);
  под ним подсказка «остатки агентств + резерв = …», чтобы целиться в $40k.
  Резерв вычитается в `compute()` и показан строкой в водопаде, KPI-плашкой
  (когда > 0) и в сводке отчёта. Формула:
  `available = кошельки + агентства − зарплаты − тех. расходы − резерв на агентства − кредиторка`.
- **Устойчивость.** Значение сохраняется через `PUT /api/reserves` (debounce),
  читается из БД в `getCompanyData`; при недоступности БД — дефолт 0.

### 2026-06-09 — Компания: вычет кредиторской задолженности CoinLink

- **Запрос.** В расчёт «доступно к выводу» добавить кредиторскую задолженность
  CoinLink за период **с 1 февраля текущего года по актуальную дату просмотра**.
- **Источник.** Внешняя read-only БД CoinLink (`tracker`). Цифра берётся
  **готовыми функциями самой БД**, чтобы точно совпадать с BI «ЦУ Payments» →
  «Кредиторская задолженность» (ручной пересчёт по сырому представлению
  `coinlink_payable` итог BI не воспроизводил):
  `coinlink_payable_total(from, to)` — одна цифра, `coinlink_payable_by_partner(from, to)`
  — разбивка по партнёрам. Период: `from` = 1 февраля текущего года,
  `to` = сегодня; вторая дата **не включительно** (как в BI: `from ≤ report_date < to`).
- **Реализация.** Новый клиент внешней БД на `pg` (`src/lib/coinlink/db.ts`), синк
  `src/lib/sync/coinlink.ts` → эндпоинт `/api/sync/coinlink`, который складывает
  итог и разбивку в БД приложения (модель `CoinlinkPayable`, миграция
  `20260609140000_coinlink_payable`). Воркер дёргает синк по расписанию
  (`SYNC_COINLINK_CRON`, по умолчанию каждые 30 минут) и один раз на старте.
  Формула: `available = кошельки + агентства − зарплаты − тех. расходы − резерв на агентства − кредиторка`.
- **Устойчивость (§7).** При недоступности внешней БД последнее известное значение
  сохраняется (карточка с пометкой свежести «обновлено N назад»), без обнуления.
- **Конфигурация.** Доступ к БД — через `COINLINK_DATABASE_URL` (или
  `COINLINK_DB_HOST/PORT/NAME/USER/PASSWORD`); представление и колонка даты
  настраиваются (`COINLINK_PAYABLE_VIEW`, `COINLINK_DATE_COLUMN=report_date`),
  начало периода переопределяется `COINLINK_PERIOD_FROM`. Секреты — на сервере,
  в репозиторий не коммитятся.

### 2026-06-08 — Крипта: корректный сбор TRON и устойчивость к сбоям

- **USDT-TRC20** теперь читается напрямую с контракта токена (вызов `balanceOf`),
  а не из ненадёжного кэш-списка токенов на аккаунте — баланс USDT в сети Tron
  отображается корректно (раньше мог быть пустым/нулевым).
- **TRX** засчитывается только свободный (нестейканный) — см. §9.5.
- **Устойчивость к сбоям (реализация §7).** Провайдеры балансов (BTC/ETH/TRON/TON)

## 11. Инфраструктура: авто-деплой (CI/CD)

Выкатка новой версии автоматизирована — ручные действия на сервере при обычном
обновлении не нужны.

**Как устроено:**

- Код и история — в GitHub. Прод-версия живёт в ветке `claude/dreamy-johnson-pUcCJ`
  (она же ветка по умолчанию репозитория).
- При любом изменении в этой ветке срабатывает GitHub Actions
  (`.github/workflows/deploy.yml`): раннер GitHub заходит на сервер (VPS) по SSH и
  выполняет `git pull` + `./deploy.sh` — пересборку и перезапуск Docker-контейнеров
  (приложение, база, воркер синхронизаций, Caddy/HTTPS).
- Доступ CI к серверу — по отдельному SSH-ключу. Приватный ключ и адрес сервера
  хранятся в **GitHub Secrets** (`VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`); в коде их нет.
- Секреты приложения (`.env`, `secrets/`) остаются на сервере и в деплое не
  участвуют — CI к ним не обращается, только перезапускает контейнеры, которые их
  читают.
- Авто-деплой включается переменной `DEPLOY_ENABLED=true` (Settings → Variables).
  Пока её нет — workflow тихо пропускается, ничего не выкатывается.
- Запустить деплой можно и вручную: вкладка **Actions → Deploy to VPS → Run workflow**.
  Логи каждого деплоя видны там же.

**Диагностика сервера:** отдельный ручной workflow «Verify server config»
(`.github/workflows/verify-server.yml`) по SSH проверяет, заданы ли нужные ключи в
`.env` на сервере. Выводит только «задан / не задан», без самих значений.

**Разовая настройка (ключ, секреты, предусловия)** подробно описана в `DEPLOY.md`,
раздел «Авто-деплой (CI/CD)».
