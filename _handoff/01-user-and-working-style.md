# 01 — Заказчик и стиль работы

## Кто заказчик

Владелец бизнеса (компания + личные финансы), для которого этот дашборд —
рабочий инструмент учёта собственного капитала. Не разработчик: общается
постановкой задач «по-человечески», на стороне ассистента — вся техническая
реализация, развёртывание и эксплуатация.

- Язык общения — **русский**, всегда.
- Email в контексте сессий: `alexander_finance@bestcompany.pro` (автор коммитов
  со стороны заказчика) и `admin_unico@bestcompany.pro`.
- Доступа к серверу у ассистента нет напрямую — команды на VPS выполняет заказчик
  копипастой (поэтому инструкции для него пишутся пошагово и дружелюбно, как в
  `DEPLOY.md`).

## Как заказчик ставит задачи

- Короткой формулировкой результата: «хочу видеть X», «добавь ползунок Y»,
  «цифра должна совпадать с BI», «подтягивай курс с такого-то сайта».
- Часто указывает конкретный внешний источник данных (nums888.io, getgems,
  CoinMarketCap, конкретная БД CoinLink) — это требование, а не предложение.
- Ценит, когда цифры **совпадают с эталоном** (например, кредиторка CoinLink
  должна в точности совпасть с дашбордом BI «ЦУ Payments»). Если ручной пересчёт
  не сходится с эталоном — брать готовую цифру из источника (функции БД), а не
  изобретать свою формулу.

## Что заказчик ценит (выведено из истории проекта)

1. **Честность данных.** Никаких выдуманных/демо-цифр в продакшне. Был отдельный
   фикс «графики неактуальные», когда линии рисовались из mock — это считается
   багом. Графики и проценты должны строиться на реальных снимках.
2. **Устойчивость к сбоям (PRD §7).** Внешний источник упал — показываем последнее
   известное значение с пометкой свежести, не обнуляем. Это повторяется почти в
   каждой доработке; относись к этому как к жёсткому требованию.
3. **Точность денежных расчётов и отсутствие двойного счёта (PRD §9).** Логика
   движения денег между «личным» и «компанией» продумана так, чтобы сумма нигде
   не считалась дважды. Меняя расчёты — перечитай §9 PRD.
4. **Самодокументирование.** Каждая заметная доработка фиксируется датированной
   записью в `PRD.md` раздел 10 (запрос → реализация → устойчивость →
   конфигурация). Продолжай эту традицию — заказчик читает журнал.
5. **Гибкость без правки кода.** Источники, периоды, ключи, расписания, регэкспы
   парсинга — всё через ENV. Заказчик может переключить источник, не прося новый
   деплой кода.

## Рабочий цикл (как принято)

- Разработка — в feature-ветке `claude/<имя>`. Коммит → пуш в эту ветку → PR.
- Мердж PR в прод-ветку `claude/dreamy-johnson-pUcCJ` запускает авто-деплой.
- Перед коммитом — `npm run typecheck` (и по возможности `npm run lint`).
- Коммиты по-русски, по сути изменения. PR-мерджи — с номером PR в заголовке.
- PR создаём ТОЛЬКО когда заказчик просит. Лишних комментариев в GitHub не пишем.

## Тон ассистента

Деловой, по-русски, по существу. Технические решения объясняй простыми словами
(заказчик не инженер), но не упрощай саму инженерию. Когда что-то нельзя сделать
из песочницы (egress-фильтр режет внешний хост) — это нормально, объясни и дай
путь проверки на проде (диагностические GET-эндпоинты, workflow «Verify server»).
